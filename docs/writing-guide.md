# 執筆規約(全世界線共通)

SAA-C03の用語集(441語)を連作お仕事小説で網羅するプロジェクトの共通ルール。世界線(舞台設定)に依存しない規約をここに置く。各世界線の設定は `universes/<name>/universe.md` を参照。

## コンセプト

- 各編は1つのtaxonomy_familyの用語群を担当し、約5,000字で「文脈と意思決定」ごと記憶させる。
- 物語の山場は必ず**技術選定の分岐**。「なぜそれを選び、なぜ他を捨てたか」を会話と思考で描く。
- 全編読了で441語すべてに物語の文脈が付くことがゴール。

## ファイル規約

- 配置: `stories/<family>/<NN>_<タイトル>.md`(NNはfamily内の通し番号)
- 各編の冒頭に front matter を付ける:

```yaml
---
universe: photorim          # universes/ のフォルダ名
family: storage_architecture
episode: 1                  # family内の通し番号
terms:                      # この編が担当するterm_id(カバレッジ検証に使う)
  - s3_standard
  - ...
---
```

- カバレッジは `tools/check_coverage.py` で機械検証する(term_idは用語集YAMLに存在すること、familyの全語がいずれかの編で担当されること)。

## 本文ルール

1. 三人称・お仕事小説風。現実的なトラブル(請求書、苦情、監査、障害)から始める。
2. 各選択の**棄却理由**(なぜ競合サービスを選ばないか)を必ず台詞か地の文に入れる。
3. 試験で問われる具体値(日数、上限、時間、割合)を物語に自然に埋め込む。
4. 1編につき最低1つ「失敗または手痛い学び」を入れる(記憶のフック)。
5. 本文は4,500〜6,000字。表を多用する編は超過可だが7,000字程度まで。
6. 割当用語はすべて本文に登場させる。
7. **term_idを本文に書かない**: 地の文・台詞ではAWSの自然な名称(「FSx for Lustre」「テープゲートウェイ」「パイロットライト」)を使う。`fsx_lustre` のようなterm_idはfront matterと用語コラムの見出し専用。
8. **試問口調の禁止**: 「問いを返す」キャラクターを口頭試験官として書かない(「言ってみろ」「答えてみろ」の連発禁止)。問いは状況への問い(「で、どうする?」「数字はどう出てる?」)として置き、説明の主体は場面ごとに入れ替える。教える側が常に正解を持つ構図を避け、学ぶ側が自力で辿り着く場面を必ず作る。
9. **メタ参照の禁止**: 本文(地の文・台詞)に「前編」「第◯編」「シリーズ」「この章」など書誌的な自己言及を書かない。過去の出来事は、登場人物の記憶や出来事の呼び名(「あの請求書騒ぎ」「ゲームデーの訓練」「先週」)として参照する。末尾の用語コラム・クイズでの章参照は可。

## 末尾セクション(必須)

### 用語コラム

「## 用語コラム — この章の登場用語と決め手」として、割当用語を1語ずつ参考書のコラム風に解説する。形式:

```markdown
### term_id(日本語表示名)

**一行の決め手(太字)。** 2〜4文のコラム本文。①物語のどの場面で登場したかへの参照(「美咲が〜した場面」)、②試験での判断基準(どの要件語で選ぶか)、③定番のひっかけ(どの選択肢と混同させられるか)を含める。読み物として面白く、しかし正確に。
```

- 一行決め手は試験直前の流し読みに耐える密度にする。
- コラム本文は物語への参照で記憶を呼び戻す構造にする(物語が索引、コラムが辞書)。

### 確認クイズ

3問、答え付き。物語の意思決定を抽象化した問いにする(固有名詞を入れ替えても解ける形)。

## レビュープロセス(二段階チェック)

すべての新作・改稿は、マージ前に以下の二段階レビューを通す。

### 1. 物語レビュー(universe整合)

- 人物の言動・口調が `universes/<name>/universe.md` の設定(中心の問い、方言濃度、禁止事項)と一致しているか
- 年表・伏線との矛盾がないか(回収すべき伏線を誤って先取り・破棄していないか)
- 災害・障害の扱いが世界線の原則(AZ名と物理位置を結び付けない等)に従っているか
- 山場が技術選定の分岐になっており、失敗または手痛い学びがあるか

### 2. 技術レビュー(仕様照合)

- 本文・用語コラム・クイズ中の数値、制約、サービス挙動を用語集YAMLおよびAWS公式ドキュメントと照合する
- 「単純化しすぎて誤りになっている」表現(例: バックアップがあるから大丈夫)を検出する
- レビュー結果は表(主張|出典|判定)で残し、PRに添付する

## 品質チェックリスト(監修用)

- [ ] front matterのtermsと用語コラムの見出しが一致
- [ ] 割当用語が本文に全登場
- [ ] 各選定に棄却理由がある
- [ ] 具体値が最低5つ埋め込まれている
- [ ] 失敗イベントがある
- [ ] 仕様の事実誤認がない(数値・制約は用語集YAMLと照合)
- [ ] 既刊との世界線整合(人物・年表は universe.md と照合)
