# 世界線: フォトリム(photorim)

写真・動画共有サービスを運営する中堅企業「フォトリム社」を舞台とした世界線。SAA-C03短編小説集のシリーズ第1作。

この世界線では、AWSサービス名を説明のために置くのではなく、**神戸で記憶を預かる会社が、請求書、誤操作、買収、災害、復旧、監査、家族の事情に向き合う中で、AWSの設計判断を身につけていく**ことを主軸にする。

## シリーズの核

> フォトリムは写真を守る会社ではない。  
> 写真を必要とする人が、必要な時に取り出せる状態を守る会社である。

日常では、家族、学校、結婚式、法人イベントの記録を預かる。非常時には、自治体や地域団体が被害状況、避難所、復旧記録を共有する基盤にもなる。フォトリムは医療・消防の基幹システムではないが、災害時には「日常の思い出のサービス」から「地域の記録のサービス」へ役割が変わる。

そのため、このシリーズで繰り返し問うべき設計上の問いは次の通り。

- そのデータは、誰が、いつ、どの単位で戻すのか。
- その構成は、壊れた時に誰が操作できるのか。
- その復旧順序は、顧客との約束に合っているのか。
- そのコストは、月末の請求書で説明できるのか。
- その権限操作は、監査に書けるのか。
- その判断は、堂島がいなくてもチームで再現できるのか。

## 舞台

### 本社

- 神戸・旧居留地の古いビルを改装したオフィス。
- 三宮から歩ける。窓の外に港の気配があり、夜はメリケンパークの灯りが見える。
- ビル自体は震災後に補修されて残った建物という設定にする。新しいスタートアップの内装と、古い街の記憶が同居している。

神戸を舞台にする理由は、写真・記録・失われたもの・戻せるものという主題と、阪神・淡路大震災の記憶が自然につながるため。美咲は震災を直接覚えていない世代だが、両親から「残していたつもりのものが失われる」怖さを聞かされて育った。

### 東京拠点

- 大手町または品川に小さな営業・法人対応拠点。
- 大手法人、学校法人、自治体、メディア企業との商談は東京で多い。
- 堂島へのヘッドハントも東京経由で来る。
- 堂島の両親も東京在住で、彼が神戸に残り続けることの葛藤になる。

### 大阪・旧データセンター

- 買収した東雲アーカイブズ社の旧オンプレ資産があった場所。
- 南港または大阪湾岸部の倉庫型DCを想定。
- 矢吹の過去、テープライブラリ、NetApp/ZFS、レンダリングファーム、Storage Gateway/DataSync/Snowファミリーの回に接続する。

### 顧客拠点

- 高知、和歌山、三重、徳島、宮崎など、南海トラフを考える上で物語に絡めやすい地域に自治体・学校・地域団体顧客がある。
- 仙台は青柳の出身地として、東日本大震災の記憶とログ・連絡・復旧の感覚に接続する。

## 方言・言葉遣いの設計

### 会話サンプル

普段の設計レビューでは、美咲は標準語寄り。

```text

ただし、ストーリー機能は対象外です。7日で消えるので、IAに置く意味がありません」

堂島は腕を組んだまま聞いていた。

「取り出し料金は見た？」

「見ました。30日以降のアクセスはかなり落ちています。ただ、法人プランだけは読めないので、Intelligent-Tieringを候補にします」
```

緊急時には、美咲の言葉に神戸の地が出る。

```text

サムネイルだけやなくて、原本のプレフィックスも拾ってます」
```

堂島は東京出身なので、関西弁の決め台詞は使わない。

```text
「いい判断だと思う」
「安くする判断と、戻せる判断は分けよう」
「今は切り替えるより、切り替えられる状態にする方が安全だ」
```

## 会社・サービス設定

- **フォトリム**: 写真・動画共有サービス。ユーザー数成長中。動画機能が当たり、有料会員と単発課金を開始。
- **個人向け**: 家族、旅行、子どもの写真を保存・共有する。
- **学校・保育園向け**: 行事写真を保護者へ配信する。繁忙期アクセス、認可、署名付きURL、保護者問い合わせが絡む。
- **結婚式場・イベント向け**: 高解像度写真・動画納品。大容量アップロード、Transfer Acceleration、Multipart Upload、編集素材共有が絡む。
- **法人メディア管理**: 写真・動画素材の長期管理。EFS/FSx/S3 Glacier/IAM/KMS/監査ログが絡む。
- **自治体・地域団体向け災害記録**: 被害状況、避難所、復旧記録を共有する。DR、RTO/RPO、Object Lock、Multi-Region、読み取り優先運用が絡む。
- **東雲(しののめ)アーカイブズ社**: 買収した映像アーカイブ会社。オンプレDC、テープライブラリ、NetApp、ZFS、レンダリングファームを保有していたが、移行完了しDC閉鎖済み。

## AWSアーキテクチャ設定

### 基本方針

- 本番リージョン: Asia Pacific (Tokyo) `ap-northeast-1`
- DRリージョン: Asia Pacific (Osaka) `ap-northeast-3`
- グローバル配信: CloudFront
- DNS/切替: Route 53、将来的にAWS Application Recovery Controllerを検討
- 本文では、特定のAZ名を物理所在地として扱わない。`ap-northeast-1a` などのAZ名はアカウントごとに物理AZへの対応が異なるため、物語上も「東京リージョンの一部AZ」「大阪リージョンのDR環境」の粒度で扱う。

### 初期状態

| 領域 | 初期状態 | 物語上の問題 |
|---|---|---|
| 本番 | Tokyo中心 | Osaka DRが未成熟 |
| S3 | すべてStandardから始まる | コスト増、Lifecycle未整理 |
| DB | RDS/Aurora Multi-AZ | リージョンDRは未完成 |
| CDN | CloudFront | オリジン障害時の切替設計が甘い |
| 管理アクセス | 踏み台EC2あり | SPOF、監査不足 |
| NAT | 1AZ寄せ | AZ障害で外向き通信停止 |
| バックアップ | 存在するが復元演習が不十分 | 「戻せる」と証明できない |
| IaC | 一部手作業 | DR時に再現できない |
| 監査 | CloudTrailはある | 見る人・使う手順が曖昧 |
| 運用 | 堂島依存 | 人間SPOF |

### 成長後の目標

| 領域 | 成長後 |
|---|---|
| 本番 | Tokyo Multi-AZ |
| DR | Osaka Pilot Light / Warm Standbyを事業要件に応じて使い分ける |
| データ | S3 CRR、AWS Backup cross-Region、必要に応じてcross-account隔離 |
| DB | Aurora Global Database、DynamoDB Global Tables、PITRを要件に応じて検討 |
| 配信 | CloudFront + Origin Failover |
| DNS/切替 | Route 53 / AWS Application Recovery Controller |
| 運用 | SSM Session Manager、break-glass role、Runbook、ゲームデー |
| 監査 | CloudTrail、Config、GuardDuty、Security Hub |
| コスト | Storage Lens、Cost Explorer、Budgets、CUR |
| 人間系DR | 堂島が不在でも判断できるチーム |

### 災害の扱い

南海トラフを扱う場合、特定のAWS AZや設備がどのように被害を受けるかは断定しない。AWS障害そのものを派手に描くより、**AWSが動いていても、社会、顧客、通信、運用チーム、承認経路が同時に揺らぐ**状況として描く。

例:

- 南海トラフ地震臨時情報が出る。
- 神戸本社に出社制限がかかる。
- 高知・和歌山・三重の自治体/学校プランで写真アップロードが急増する。
- Tokyo本番は稼働しているが、神戸・大阪在住メンバーの通信や家庭事情が不安定になる。
- Osaka DRは存在するが、切替判断には事業優先度、RTO/RPO、運用者のログイン経路が絡む。
- 社内IdPや承認者不在など、AWS外の依存が復旧を遅らせる。

## 登場人物

### 瀬名美咲(せな・みさき)

```yaml
age: 31
birthplace: 神戸
role: インフラ/SRE寄りクラウドエンジニア
base: 神戸本社
language:
  work: 標準語寄りの丁寧語。感情が動くと神戸・阪神間の言葉が出る
core_question: それは本当に戻せるんですか
```

主人公。1995年、阪神・淡路大震災の年に神戸で生まれた。本人に震災の記憶はないが、両親から繰り返し聞かされて育った。母は妊娠中に震災を経験し、父は濡れたアルバムを乾かした話を何度もしている。家には端が波打った古い写真が残っている。

美咲は写真を感傷的に語るタイプではない。普段は請求書、アクセスログ、復旧時間、設計表を見る。しかし、データを失う話になると声が硬くなる。初期は責任感が強く、一人で抱える。堂島に質問する前に自分で調べ込み、青柳のミスも自分で直そうとする。

成長後は、人は間違う前提で戻せる仕組みを作る人になる。

| 初期 | 成長後 |
|---|---|
| 自分がミスしなければよい | 人はミスする前提で設計する |
| 堂島に正解を求める | チームに問いを配る |
| サービス名で選ぶ | RTO/RPO、復元単位、事業優先度で選ぶ |
| コスト削減を単独で考える | 取得料金、復元時間、運用負荷まで見る |
| 障害を恐れる | 障害時に判断を記録する |

### 堂島要(どうじま・かなめ)

```yaml
age: 42
birthplace: 東京
role: シニアソリューションアーキテクト / 技術顧問
base: 神戸在住、東京出張多め
family:
  parents: 東京在住の70代。父に持病あり
  spouse: 神戸出身
  child: 小学生
language:
  default: 標準語。関西弁は理解するが、基本的に話さない
core_question: その設計は、誰が壊しても戻せるか
```

先輩エンジニア。東京出身。仕事でも家庭でも基本は標準語。神戸に長く住んでおり関西弁は理解するが、自分から自然に使う人ではない。関西弁の決め台詞は使わない。

2011年、東京で東日本大震災を若手インフラエンジニアとして経験した。当時はAWSが普及し始めていたが、現在ほどDR設計パターンや運用知見は整っていなかった。オンプレと初期クラウドが混在し、バックアップも手順書もあったが、誰が判断し、どの順番で戻し、顧客に何を説明するかが曖昧だった。技術的には戻せるはずのシステムが、実際にはなかなか戻らなかった。

その経験から、堂島は「壊れない構成」よりも「壊れた時に人が動ける構成」にこだわる。

東京の大手企業や外資系クラウドコンサルからヘッドハントがある。東京に戻れば親の近くに住め、報酬も上がる。それでもフォトリムに残る理由は、2011年にできなかったことを、神戸でやり直しているから。彼が本当に作りたいのは、自分がいなくても戻せるチーム。

堂島の会話は短く、問いを返す。

```text
「数字を見よう」
「要件語を読もう」
「安くする判断と、戻せる判断は分けよう」
「俺がいないと回らないなら、俺が一番危ない単一障害点だ」
```

### 青柳凛(あおやぎ・りん)

```yaml
age: 24
birthplace: 仙台
role: ジュニアSRE / 運用自動化担当

language: 標準語。関西弁は使わない
```

新人。読者の代弁者として素朴な質問をする。小学生の頃に東日本大震災を経験し、家族と連絡が取れない時間の記憶がある。神戸本社の中では少し外側の視点を持つ。

第5編で誤削除事故を起こす。失敗を笑いにしない。青柳の失敗から、CloudTrail、S3 Versioning、Object Lock、Config、EventBridge、IAM least privilege、permission boundary、Runbookが生まれる。

成長後は、ミスをしない人ではなく、ミスが起きても検知し、止め、戻せる仕組みを作る人になる。

```text
「CloudTrail、見ます。誰が何をしたか、まずそこから確認します」
```

### 狩野沙耶(かのう・さや)

```yaml
age: 36
birthplace: 東京または横浜
role: プロダクト責任者 / 法人・自治体顧客担当
base: 東京拠点と神戸を往復
```

現行設定の「法務部」から、法人・自治体顧客を持つプロダクト責任者へ拡張する。監査・契約・SLAの話にも関与するが、単なる法務担当ではなく、顧客との約束を言語化する人物。

```text
「全ユーザーを同時に戻すのが理想なのは分かっています。
でも今は、自治体プランと学校プランを優先してください。
古い退会データは、今回のRTO対象から外します」
```

### 守屋仁(もりや・ひとし)

```yaml
age: 49
birthplace: 京都南部または滋賀
role: 情シス兼総務 / BCP担当
base: 神戸本社
language: 丁寧な関西寄り。危機時は静かに関西の言葉が出る
```

昼行灯枠。普段は目立たない。非常用連絡網、MFAの予備手段、避難訓練、端末管理、社内IdP、BCPの話ばかりするため、若手からは少し面倒な人と思われている。

しかし南海トラフ回で見せ場が来る。神戸本社が停電し、Slackが不安定になり、社内IdPに入れない人が出る。AWSは動いているが、人が操作できない。その時、守屋が紙のBCP手順、非常用端末、別キャリア回線、break-glass手順、代替承認ルートを出す。

```text
「AWSは動いてます。でも、誰もログインできひんかったら、止まってるのと同じです」
```

## 人間関係の変化

### 美咲と堂島

初期は先生と生徒。中盤は問いを渡す人と受け取る人。終盤は、同じ会議で別の観点を持つアーキテクト同士になる。

堂島は助けすぎることがチームの成長を止めると気づく。美咲は堂島に正解を求めるのではなく、チームに問いを配るようになる。

### 美咲と青柳

初期の美咲は、青柳のミスを見ると自分がやった方が早いと思う。しかし、青柳の失敗を仕組みに変えることでチームが強くなる。最終的に美咲は、ログ調査や再発防止を青柳に任せる。

### 美咲と矢吹

初期の美咲は矢吹を「オンプレの人」と見ている。矢吹は美咲を「クラウドの人」と見ている。二人はやがて「どの単位で戻すのか」という同じ問いに向き合う。

### 美咲と狩野

初期は対立する。狩野は「止めないで」と言い、美咲は「無理です」と返す。話が進むにつれて、狩野はRTO/RPOと顧客優先度を言語化し、美咲は技術的実現可能性とコストを説明するようになる。

### 堂島とフォトリム

堂島は東京へ戻る理由を多く持つ。親、報酬、キャリア、ヘッドハント。それでも神戸に残るのは、フォトリムで「自分がいなくても戻せるチーム」を作りたいから。

## 執筆上の注意

- `ap-northeast-1a` のようなAZ名を物理所在地として扱わない。
- 南海トラフで特定AWSリージョン/AZが落ちるとは断定しない。
- 災害描写を派手な演出に寄せず、社会・顧客・運用・家族が同時に揺らぐ状況として扱う。
- 堂島に関西弁の決め台詞を言わせない。彼は東京出身で、神戸に残っている人。
- 美咲は仕事中は標準語寄り。緊急時や家族相手に神戸・阪神間の言葉が出る。
- 関西弁を記号的に使わない。人物の出身、年齢、関係性、緊急度に合わせる。
- 矢吹を「古い人」として軽く扱わない。クラウド以前を知る復元設計の専門家として描く。
- 青柳の失敗を笑いにしない。失敗が仕組みに変わる過程を描く。
- 守屋を単なる便利キャラにしない。AWS外のDR、BCP、人間のログイン経路を背負わせる。
- 技術的に正しいが物語として不自然な会話は避ける。用語は、人物の困りごとから自然に出す。

## 参考にするAWS上の制約

- AWSのリージョン表では、Asia Pacific (Tokyo) は `ap-northeast-1`、Asia Pacific (Osaka) は `ap-northeast-3` とされている。
- AWSのAZ名はアカウントごとに物理AZへの対応が異なるため、物語上もAZ名を物理所在地として扱わない。
- AWSのDR戦略は、Backup and Restore、Pilot Light、Warm Standby、Multi-site Active/Activeのように、コスト・複雑性・RTO/RPOに応じて段階的に選ぶ。
- 詳細な仕様・料金・サービス名は変わり得るため、本文確定時には公式ドキュメントで再確認する。
