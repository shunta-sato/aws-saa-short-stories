# 世界線: フォトリム(photorim)

写真・動画共有サービスを運営する中堅企業「フォトリム社」を舞台とした世界線。シリーズ第1作。

フォトリムは、写真を預かる会社ではなく、**誰かがあとで必要とする記録を、取り出せる形で残す会社**である。日常では家族、学校、結婚式、法人イベントの記録を扱い、非常時には自治体・学校・地域団体が被害状況や避難所の様子を共有する基盤にもなる。この二面性が、ストレージ、レジリエンス、ネットワーク、セキュリティ、コスト最適化の物語を生む。

シリーズを貫く問いは一つ——**「それは本当に戻せるんですか」**。コピーがあることと、戻せることは違う。消えないことと、消せないことも違う。各編の技術選定は、最終的にこの問いへ収束する。

この世界線で繰り返し問うべき設計上の問いは次の通り。

- そのデータは、誰が、いつ、どの単位で戻すのか。
- その構成は、壊れた時に誰が操作できるのか。
- その復旧順序は、顧客との約束に合っているのか。
- そのコストは、月末の請求書で説明できるのか。
- その権限操作は、監査に書けるのか。
- その判断は、瀬名がいなくてもチームで再現できるのか。

## 舞台

- **本社(神戸)**: 旧居留地周辺の古いビルを改装したオフィス。三宮から歩ける距離にあり、窓を開ければ港の気配がする。開発・SRE・プロダクトの中心。
- **東京拠点**: 大手町。法人営業、自治体・大企業向け商談、採用、セキュリティ/コンプライアンス機能(風間の所属)を持つ。
- **大阪**: 買収した東雲アーカイブズ社の旧データセンターがあった土地(現在は閉鎖済み)。AWSのDR先としての大阪リージョンとともに、物語上の「もう一つの拠点」。
- **顧客地域**: 関西圏・首都圏に加え、高知・和歌山・三重・徳島・宮崎など、南海トラフを意識せざるを得ない地域の学校・自治体・地域団体。

## 会社・サービス設定

- フォトリム: 写真・動画共有サービス。ユーザー数成長中。動画機能が当たり、有料会員と単発課金(決済系)を開始。
- **動画参入の経緯(正典)**: 動画は式場プラン+招待制の一般先行枠のベータとして開始。著名人の挙式動画を契機に想定の20倍へバズし、招待枠を二度拡大。GA(一般公開)前倒し圧力の中で、全データStandard起因のストレージ原価危機を6週間で乗り越えた(storage/01)。
- **個人向け**: 家族写真、旅行、子どもの成長記録、短期共有のストーリー機能(7日で自動削除)。
- **学校・保育園向け**: 行事写真を保護者へ配信。行事シーズンのアクセス急増、認可、署名付きURL、配信遅延が課題になる。
- **結婚式場・イベント向け**: 高解像度写真・動画の納品。大容量アップロード、編集スタジオとのファイル共有が絡む。
- **法人メディア管理**: 放送局・制作会社の素材長期保管。監査、KMS、Object Lock、Glacier階層、権限管理が絡む。
- **自治体・地域団体向け災害記録**: 被害状況、避難所、復旧記録の共有。平時は小さな契約でも、**災害時には最も止めにくいサービス**になる。事業優先度の議論で必ず顔を出す。
- 東雲(しののめ)アーカイブズ社: 買収した映像アーカイブ会社(大阪)。オンプレDC(テープライブラリ、NetApp、ZFS、レンダリングファーム、素材管理DB=PostgreSQL)を保有していたが、移行完了しDC閉鎖済み。素材管理DBは移行期の時間制約で**スキーマ未見直しのリフト&シフト**でRDSへ移った(S4で顕在化する設計負債の正典)。

## AWSアーキテクチャ前提

- 本番リージョン: 東京。DRリージョン: 大阪。
- **コスト構造(正典)**: 写真時代のAWS費用はコンピューティング(サムネイル生成・画像処理)と配信転送が支配的で、S3保存費は全体の2割弱の「静かな行」だった。動画参入(コンテンツ単価が写真の約1000倍)で保存費が主役級に転じた。
- **AZ名を物理位置として扱わない**。AZ名はアカウントごとの表示名であり、特定の地理位置や震災影響範囲に紐付けて描かない。
- 初期状態(第1〜6編の時点):
  - S3はStandard中心から始まり、コスト爆発を契機にStorage Class/Lifecycle設計が進んだ。
  - RDS/Aurora/EBS/EFS/FSx/S3が混在し、バックアップは整備されたが「復元単位」の設計は未成熟。
  - CloudFrontは利用中。オリジン障害時の設計は整ったが、災害時の優先順位は未整理。
  - **残存SPOF**: NAT Gateway 1AZ、踏み台1台、東雲由来のバッチサーバー1台。
  - **人間SPOF**: 障害対応の判断が瀬名個人に集中している。
- 成長後の目標: Multi-AZ設計、適切なMulti-Region DR、Runbook、SSM Session Manager、break-glass手順、CloudTrail/Configによる監査。「コピーがある」ではなく「**誰が、どの単位で、どの順序で、いつまでに戻すか**」を説明できる状態。

## 災害・障害の扱い

日本は震災の記憶とリスクを持つ。フォトリムでは南海トラフや大規模地震を、AWSの特定AZが壊れる話として断定的に描かない。扱うべき中心は、**社会、通信、顧客、運用者、承認系統が同時に揺らぐ状況**である。

| 障害レベル | 物語上の表現 | AWS設計テーマ |
|---|---|---|
| AZ障害 | 東京リージョン内の一部リソースや経路が使えない | Multi-AZ, ALB, RDS Multi-AZ, NAT Gateway per AZ |
| リージョン障害 | 東京リージョンを主系として使えない | 大阪DR, Route 53, ARC, Backup/Replication cross-Region |
| 国内広域災害 | 本社、顧客、通信、運用者が同時に影響を受ける | BCP, remote operations, break-glass, Runbook |
| 運用拠点障害 | AWSは動いているが、人がログインできない | IAM Identity Center, SSM Session Manager, 非常時承認 |
| 誤操作・内部障害 | 削除、タグ誤設定、権限過多、復旧遅延 | CloudTrail, Config, Versioning, Object Lock, permission boundary |

### 会話サンプル

普段の設計レビューでは、美咲は標準語寄り。

```text
「30日後にStandard-IAへ移す案で進めます。
ただし、ストーリー機能は対象外です。7日で消えるので、IAに置く意味がありません」

瀬名は腕を組んだまま聞いていた。

「取り出し料金は見た？」

「見ました。30日以降のアクセスはかなり落ちています。ただ、法人プランだけは読めないので、Intelligent-Tieringを候補にします」
```

緊急時には、美咲の言葉に神戸の地が出る。

```text
「待ってください。そのLifecycleルール、今入れたらあかんです。
サムネイルだけやなくて、原本のプレフィックスも拾ってます」
```

瀬名は東京出身なので、関西弁の決め台詞は使わない。

```text
「いい判断だと思う」
「安くする判断と、戻せる判断は分けよう」
「今は切り替えるより、切り替えられる状態にする方が安全だ」
```

## 登場人物

### 堂島美咲(どうじま・みさき) — 「それは本当に戻せるんですか」

- 31歳。神戸生まれ神戸育ち。前職は大阪のSIerで、クラウドは入社後実質3年目。動画ベータが初のインフラ主担当(storage/01)。1995年春、阪神・淡路大震災の年に生まれた。本人は震災を覚えていないが、両親から繰り返し話を聞かされて育った。実家には、親族が水から救い出して乾かした、端の波打った古いアルバムが残っている。**写真が「戻ってきた記録」であることを、家庭の歴史として知っている**。
- 役割: 主人公。インフラ/SRE寄りクラウドエンジニア。三人称で描く。
- 強み: 数字を見る。調べる。障害後に逃げない。
- 弱み: 一人で抱えやすい。正解を急ぎすぎる。人に任せるのが苦手。
- 成長アーク: サービス名で考える人から、RTO/RPO、復元単位、事業優先度、人的運用まで含めて判断する人へ。最終的には瀬名の問いを自分が後輩に渡す側になる。

### 瀬名要(せな・かなめ) — 「その設計は、誰が壊しても戻せるか」

- 42歳。東京出身、現在は神戸在住。妻と小学生の子どもがいる。東京に70代の両親(父に持病)。
- 役割: シニアソリューションアーキテクト。答えを教える人ではなく、**問いを返す人**。
- 原体験: 2011年、東京で東日本大震災を若手インフラエンジニアとして経験。バックアップも手順書もあるのに、誰が判断し、何をどの順番で戻し、顧客に何を説明するかが曖昧で、技術的には戻せるはずのシステムが戻らなかった。
- 動機: 「壊れない構成図」ではなく「**壊れた時に人が動ける設計**」を作る。フォトリムに残る理由は、あの「戻せるはずなのに戻せない現場」のやり直し。自分がいなくても戻せるチームを残したい。
- 構造的課題: **瀬名自身がチームの人間SPOF**。東京の大手やコンサルからのヘッドハント、両親の介護問題により、「瀬名がいない日」がいずれ訪れる。実際、動画ベータの設計期間は東京の実家の事情で約2か月半不在だった(storage/01。**事情の詳細は作中で説明しない**——S3⑤・S8で悪化する事情の、説明されない初出)。復帰後は問いと検算と、美咲に見えない根回しに徹した。
- 口癖: 「数字を見よう」「要件語を読もう」「戻す順番を決めよう」。説教臭くしない。助けすぎない。物語が進むほど、前に出る回数を意図的に減らす。

### 矢吹智弘(やぶき・ともひろ) — 「そのデータは、どの単位で戻すんや」

- 58歳。尼崎出身。買収先・東雲アーカイブズ社の元データセンター運用責任者。DC閉鎖後、フォトリムのクラウド運用チームに合流。
- 専門: NAS/SAN、テープ、NetApp、ZFS、レンダリングファーム、夜間作業、復元単位の設計。
- 立ち位置: 元クラウド懐疑派。クラウドが嫌いなのではなく、**復元できない構成図を信用しない**。
- 見せ場: 「S3にコピーがある」で満足するチームに、ユーザー単位・アルバム単位・撮影日単位という「顧客が必要とする復元単位」を問い直す。
- 話し方: 大阪寄りの関西弁。漫才口調にしない。重みのある現場の言葉で本質を突く。オンプレ時代の比喩(テープ、倉庫、トラック)で核心を言い当てる。

### 青柳凛(あおやぎ・りん) — 「次に同じミスが起きたら、自動で止められるか」

- 既刊設定: 本番バケットの誤削除事故(storage/05)。
- 成長アーク: ミスをしない人になるのではなく、**ミスが起きても検知し、止め、戻せる仕組みを作る人**になる。CloudTrail・EventBridge・自動化が武器になっていく。
- 弱み: 焦ると確認を飛ばす。叱責を恐れて報告が遅れがち——この性質自体が後の物語の事件になる。

## 運用語彙(再利用する道具立て)

- **週次の時計**: 大きな期限は「N週間ある」ではなく「1週間がN回ある」と刻む(傾向→確定→修正→テスト→予備→本番)。storage/01で確立。以後の総力戦回で再利用してよい。
- **Stagingは本番ではない**: Stagingの綺麗なデータは、本番の歴史(旧形式・例外・失敗パターン)を再現しない。適用前に本番実データのサンプリングと突き合わせる。storage/01の単価見逃しと誤投入事件の共通の根。

## 禁止事項・注意事項

- 実在のAWS内部事情、AZの物理位置、AZ名と地理的位置の対応を創作しない。
- 「南海トラフで特定のAZ/リージョンが必ず落ちる」と断定しない。「東京リージョンなら影響を受けない」とも断定しない。社会、通信、顧客、運用者、承認系統への影響を描く。
- 災害を派手な演出の道具として軽く扱わない。人物の記憶と事業上の責任に根ざして描く。
- 関西弁を記号的に盛らない。
- 瀬名が全部を解決しない。優秀な人がSPOFになる構造そのものを物語の課題にする。
- 「バックアップがあるから大丈夫」「Object LockがあるからDR不要」「Active/Activeなら最善」のような単純化を避ける。

## 参考にするAWS上の制約

- AWSのリージョン表では、Asia Pacific (Tokyo) は `ap-northeast-1`、Asia Pacific (Osaka) は `ap-northeast-3` とされている。
- AWSのAZ名はアカウントごとに物理AZへの対応が異なるため、物語上もAZ名を物理所在地として扱わない。
- AWSのDR戦略は、Backup and Restore、Pilot Light、Warm Standby、Multi-site Active/Activeのように、コスト・複雑性・RTO/RPOに応じて段階的に選ぶ。
- 詳細な仕様・料金・サービス名は変わり得るため、本文確定時には公式ドキュメントで再確認する。
