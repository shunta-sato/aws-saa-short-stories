# 引っ越しと四つのFSx — ファイルストレージ編

*SAA-C03 短編小説集 / S1-03 — storage_architecture*

---

夏の終わり、社内ポータルに正式な発表が出た。フォトリム社は、大阪の映像アーカイブ会社「東雲アーカイブズ社」を買収する。同社のシステムは、半年をめどにAWSへ移行する——。デューデリジェンスの噂を聞いてから、季節がひとつ動いていた。発表の3日後、堂島美咲は移行プロジェクトのインフラ担当になっていた。

「先方の中心はファイルサーバー群だ。それなりに歴史がある」と瀬名要は言った。フォトリム唯一のシニアソリューションアーキテクト。人選の理由を、美咲は聞かなかった。保存の危機をくぐった人間に、次はオンプレの山を見せる——問いの続きのような人事だと、自分でも思ったからだ。

歴史がある、という言い回しの不穏さを、美咲は最初の大阪出張で理解した。三宮から阪神電車に揺られて小一時間、雑居ビルの並びに東雲アーカイブズはあった。エレベーターを地下二階で降りると、空気が変わる。冷気と、かすかな機械油の匂い。年代物のラックの列の奥から、ファンの低い唸りが絶え間なく聞こえていた。

案内に立ったのは、矢吹智弘だった。五十八歳。尼崎の生まれで、東雲アーカイブズの元データセンター運用責任者。この地下で30年、テープとディスクと空調を守り、夜中の警報で呼び出される側を勤め上げてきた人だ。

「クラウドの人か」矢吹は美咲を上から下まで一瞥し、その値踏みを隠さなかった。「言うとくけどな、うちのファイルサーバーは複雑やぞ。NFSもSMBもある。ADで部署ごとにアクセス制御をかけてる。レンダリングファームは、生半可なストレージやと速度が出えへん。全部S3に放り込んだら終わり、と思てるんやったら、帰ってんか」

「思ってません」と美咲は答えた。半分は本当だった。残りの半分——全部EFSに載せればだいたい片付くのでは、という見立ては、口に出さずにおいた。その見立ては、棚卸しが進むにつれて静かに崩れていくことになる。

---

矢吹に連れられて現場を回った棚卸しの結果、移行対象は五つに割れた。

ひとつ目は、社内ツール群が使うLinux系のNFS共有。スクリプト置き場とログ集約で、容量はせいぜい数百GB。ふたつ目は、Windowsファイルサーバー。プロトコルはSMB、認証はActive Directory、フォルダごとにNTFSのACLで部署別の権限が効いている。「経理フォルダは経理部しか開けん。当たり前やろ」と矢吹。三つ目は、矢吹が誇る映像レンダリングファーム。数十台のノードが一本の映像を分割し、全ノードが同じ素材ストレージへ並列I/Oを叩き込む。四つ目は、NetApp製のストレージ装置。SnapMirrorで東京の拠点と同期しており、しかも同じ素材をLinuxの解析班がNFSで、Windowsの編集班がSMBで触っている。五つ目は、検証チームのZFSサーバー。スナップショットから書き込み可能なクローンを切り、本番のコピーを一瞬で10個作って、壊して、捨てる。

帰りの電車で、美咲は五つの行を手帳に書き並べた。EFSのドキュメントを開いて、ふたつ目の行で手が止まった。EFSはNFSの世界の住人で、SMBを話せない。「全部EFS」は、その一行で死んだ。代わりに、調べるほどFSxという家族の名前が繰り返し出てくる。Windows、Lustre、NetApp ONTAP、OpenZFS——目的別に四人。プロトコルと運用を聞けば決まりそうな気配は、このときからあった。ただし、それを表にして矢吹の前へ出せるようになるまでには、まだ一度、転ぶ必要があった。

---

最初に手を付けたのは、ひとつ目のNFS共有だった。いちばん普通で、いちばん失敗しなさそうに見えたからだ。

置き場は**EFS Standard**。リージョナル構成で複数AZにデータを複製する、いちばん壊れにくいクラスだ。読まれなくなった過去ログは、ライフサイクル管理で低頻度アクセス向けの**IA**(Infrequent Access)へ自動で降ろして単価を下げる。ビルドキャッシュのような作り直せる中間データは**EFS One Zone**へ分けた。単一AZに置く代わりに約47%安い。作り直せないものはOne Zoneに置かない——サムネイルと原本を置き分けた、あの請求書騒ぎと同じ理屈だった。

移行計画のレビューで、矢吹が一点だけ突いてきた。

「その共有な、普段は暇やけど、月末のバッチで一気に読み書きするんや。瞬間的に太い帯域が要る。クラウドさんに、そんな芸当できるんか」

「できます」と美咲は言った。マネージドなのだから、負荷が来れば伸びるはずだ——値踏みの目に対する意地が、いつもの確認を一段飛ばさせた。EFSは既定値のまま作られ、初回の月次バッチを迎え、そして詰まった。普段の3倍の時間を食って、まだ終わらない。

深夜、自宅の台所の灯りだけを点けて、美咲はリモートでメトリクスを開いた。スループットのグラフが、天井に張り付いていた。

「……あかん、詰まっとう」

言い切った相手の顔が浮かんで、頬が熱くなった。その夜のうちに、彼女はドキュメントとメトリクスを突き合わせた。EFSの性能には軸が二つある。ひとつは**パフォーマンスモード**。汎用は低レイテンシで、Max I/Oは数千クライアント級の超並列向け——そのかわり一操作ごとのレイテンシが上がる。これは作成時にしか選べない軸だが、今回は汎用で正しく、原因ではなかった。もうひとつの軸が**スループットモード**、帯域の決まり方だ。既定のBurstingは、帯域が保存容量に比例する。数百GBしかないファイルシステムの帯域は細く、バーストクレジットを使い切れば地を這う。容量と帯域が、鎖でつながっている。

gp2の、容量とIOPSの鎖を切った日のことを思い出した。同じ形の罠に、二度はまったのだ。

切り替え先はElasticにした。負荷に応じて帯域が自動で増減し、使った分だけ払う。固定で帯域を張るProvisionedもあるが、月に一度のスパイクのために毎日分を張るのは、置き賃の無駄だ。幸い、スループットモードは後から変えられる。変えられない軸と、変えられる軸。その区別を、美咲は身銭で覚えた。

翌朝、始発に近い阪神電車で大阪へ出た。一睡もしていない目に、車内灯が白かった。矢吹の机の前に、報告書を置いた。原因、対策、再発防止——それから、「できます」と言い切ったときに確認を飛ばしていたことまで、全部書いた。

矢吹は最後まで読み、報告書を机に戻した。

「……転び方の説明ができるんやったら、上等や。詰まった言い訳から始めるやつには、ラックの鍵も渡されへん」

次の月次バッチは、普段どおりの時間で終わった。終わった日の帰り際、矢吹が黙って缶コーヒーを一本、美咲の机に置いていった。よく冷えた、甘いやつだった。

---

ふたつ目のWindowsファイルサーバーは、下調べの答えをぶつける番だった。

「ここは**FSx for Windows File Server**にします。SMB、AD参加、NTFSのACL——要件の三つとも、Windowsの言葉です。EFSはNFS専用なので土俵に上がれません。FSx for WindowsはネイティブにSMBを話して、既存のADドメインに参加できて、ACLをそのまま使えます」

「つまり」と矢吹。「経理フォルダの権限設計、やり直さんで済むんか」

「そっくり引き継げます」

「それは……正直、助かるな」矢吹の声から、針が一本抜けた。

ひとつだけ、美咲がドキュメントの隅から拾ってきた注意があった。可用性の構成——Multi-AZか単一AZか——は、作成時にしか選べない。あとからMulti-AZに変えることはできない。

「経理の共有が止まると、会社の締めが止まりますよね」

「止まる。月末なら大騒ぎや」

「なら、最初からMulti-AZで組みます。これは、あとで直せない方の軸なので」

---

三つ目のレンダリングファームは、地下フロアの主役だった。矢吹はラックの列を撫でるように歩いた。

「ここだけは譲れんで。レンダリング中、数十台が一斉に同じ素材を読みに来るんや。帯域が先に死ぬような置き場やったら、うちの仕事は止まる」

美咲の下調べは、ここでいちばん時間を食っていた。EFSのMax I/Oも検討はした——が、桁が足りない。要件に応えるのは**FSx for Lustre**だった。スーパーコンピュータの世界で使われてきた並列分散ファイルシステムで、数十、数百ノードからの同時I/Oに数百GB/s級の帯域で応える。それに、この案件向きの特技がもうひとつある。

「S3とリンクできるんです。素材は普段S3に置いておいて、レンダリングのときだけLustreへロードして、結果をS3へ書き戻す。高速ストレージを常時抱えなくていい。中間ファイル用には冗長性なしで安いscratchタイプ、消えて困るものには永続のpersistentタイプ、と使い分けます」

「Lustreか」矢吹は片眉を上げた。「……うちのファーム、ありもんの構成に近いわ。話が早いな」

---

四つ目のNetAppでは、美咲が先に問題の核心を口にした。

「同じデータを、NFSとSMBの両方で読む部門がありますよね。EFSはNFSだけ、FSx for WindowsはSMBだけ。どちらかに寄せると、片方の班の仕事が止まります。——それで、FSxの家族には四人目がいます。**FSx for NetApp ONTAP**。ONTAPそのものがマネージドで動くので、ひとつのデータを両方のプロトコルから読めます。重複排除や圧縮も、そのまま効きます」

「ONTAPがそのまま動く、て」矢吹が身を乗り出した。「ほな、SnapMirrorは。拠点間同期の、あれもか」

「ONTAP同士なので、使えます。移行そのものも、オンプレのNetAppからSnapMirrorで流せます」

「30年使うてきた道具の名前が、そのまま通じるんか」

矢吹はしばらく黙って、ホワイトボードの四行目を見ていた。何を確かめていたのかは、聞かなかった。

五つ目のZFSサーバーは、もう答え合わせのようなものだった。スナップショットから書き込み可能なクローンを量産する運用は、ZFSの機能そのものだ。だったら**FSx for OpenZFS**。オンプレの流儀ごと持ち込めて、本番のコピーを一瞬で10個作って壊して捨てる検証フローは、何ひとつ変わらない。提供プロトコルはNFS。美咲がそこまで言うと、矢吹は「それでええ」とだけ言った。

---

週の終わり、瀬名が検算に大阪へ来た。ホワイトボードには五つの行と五つの答えが並んでいる。瀬名は表を端から端まで読み、マーカーを取って、二箇所にだけ小さく印を付けた。

「あとから変えられないものに、印を付けておこう。FSx for WindowsのMulti-AZと、EFSのパフォーマンスモード。この二つは作る日に決める。あとは全部、走りながら直せる」

それだけ言うと、瀬名はもう表に手を入れなかった。

矢吹は腕を組んだまま、五行の表を見つめた。

「……つまり、こういうことか。プロトコルと運用を聞いたら、置き場所が決まる。汎用のLinux共有ならEFS。SMBとADならFSx for Windows。超並列ならLustre。NetApp資産でマルチプロトコルならONTAP。ZFS運用ならOpenZFS。——それだけか」

「それだけです」と美咲は答えた。「四種類ある、と最初に聞いたときは身構えました。でも、要件を聞く順番さえ間違えなければ、向こうから名乗り出てくれます」

「魔法やのうて、対応表か」矢吹の頬が、わずかに緩んだ。「クラウドっちゅうのは、こっちの30年をぶち壊して、一から作り直させるもんやと思てた。道具の名前がそのまま通じるんやったら——悪ない」

だが矢吹はすぐに、ぴしゃりと付け加えた。

「ただし、や。話はここで終わらんで」彼は地下の奥、締め切られた扉を指した。「あの部屋には、まだテープライブラリがある。30年分の映像原本や。地元局の報道素材——祭りの中継も、選挙の夜も。……震災のあとの街を、ヘリから撮ったやつもな」矢吹はそれだけ言って、それ以上は言わなかった。「ほんで、回線では送り切れんペタバイト級のマスターが、別棟の倉庫にまるごと眠っとる。あれをどうやって上げる気や。半年で、ネット越しにか?」

美咲は暗算しかけて、やめた。桁が、日常の暗算の単位ではなかった。

「それにな」矢吹は少し声を落とした。「あんたら、上げる話ばっかりしとるけど——そのデータは、どの単位で戻すんや。全部いっぺんか。一本ずつか。そこを決めんと、上げたところで意味がないで」

答えは、美咲にも瀬名にもまだなかった。冷えた地下フロアに、宿題の形をした沈黙が残った。

地上へ出ると、残暑の西日が街を焼いていた。帰りの阪神電車で、美咲は手帳の対応表の裏に三行だけ書いた。テープ。倉庫のマスター。戻す単位。窓の外を尼崎の工場の灯りが流れていく——矢吹が生まれて、30年通った街だ。三宮に着く頃には、三行はもう、宿題の顔をしていた。

## 用語コラム — この章の登場用語と決め手

### efs_standard(EFS Standard)

**Linux/NFS汎用共有の既定値。複数AZ複製でいちばん壊れにくい。** 東雲の社内ツール共有の移行先になったクラスで、リージョナル構成のため単一AZ障害でもデータを失わない。試験の決め手は「複数EC2から共有」「NFS」「高可用」の組み合わせ。SMBの一語があれば土俵から降りてFSx for Windowsへ渡す。

### efs_infrequent_access(EFS IA)

**触られなくなったファイルは、自動で安い階層へ。** ライフサイクル管理が最終アクセスからの日数でIAへ移し、過去ログの保存単価を下げた。S3ライフサイクルとの違いがひっかけどころ——EFSは「最終アクセス」基準で移行のみ(削除はしない)、S3は「作成からの日数」基準で削除もできる。

### efs_one_zone(EFS One Zone)

**単一AZで約47%安。ただし「作り直せるもの」限定。** ビルドキャッシュのような再生成可能な中間データの置き場に使った。AZ障害で失われる可能性と引き換えの安さなので、原本を置いてはいけない。S3 One Zone-IAとまったく同じ理屈で問われる。

### efs_performance_mode(EFSパフォーマンスモード)

**作成時にしか選べない軸。** 汎用(General Purpose)は低レイテンシで大半のケースの正解、Max I/Oは数千クライアント級の超並列向けだが一操作のレイテンシが上がる。美咲のバッチ詰まりの原因はこちらではなかった——性能問題を見たらまず「どちらの軸か」を切り分ける。あとから変更できない点がMulti-AZ構成と並ぶ設計時の要注意項目。

### efs_throughput_modes(EFSスループットモード)

**Bursting=容量連動、Elastic=自動増減、Provisioned=固定確保。あとから変更できる。** 小容量+月次スパイクの共有が既定のBurstingで詰まったのが本編の失敗。Burstingは帯域が保存容量に比例する——gp2の容量とIOPSの鎖と同じ構造だと見抜ければ、正答(Elasticへの変更)は自動的に出る。

### amazon_fsx_for_all_types(Amazon FSx)

**「どのファイルシステムをマネージドで欲しいか」で選ぶ、目的別四人家族の総称。** Windows File Server、Lustre、NetApp ONTAP、OpenZFSの4種。矢吹の到達点のとおり、プロトコルと運用要件を聞けば対応表で機械的に決まる。試験も同じ対応表で解ける——問題文の要件語をどの行に当てはめるかだけが問われる。

### fsx_windows_file_server(FSx for Windows File Server)

**SMB+Active Directory+NTFS ACLと来たら一択。** 経理フォルダの部署別権限を、ADドメイン参加でそのまま引き継いだ。EFSはNFS専用なので棄却。Multi-AZ構成は作成時にしか選べない点が運用側の分岐で、「あとからMulti-AZ化」という選択肢は誤答。

### fsx_lustre(FSx for Lustre)

**HPC級の並列I/Oと、S3とのリンクが特技。** レンダリングファームの数十台同時読み込みに数百GB/s級で応えた。素材をS3からロードして処理し書き戻す使い方と、scratch(安価・冗長なし・一時用)/persistent(永続・冗長あり)の使い分けまでがセット。「HPC」「機械学習」「動画処理」「S3のデータを高速処理」が要件語。

### fsx_netapp_ontap(FSx for NetApp ONTAP)

**NFSとSMBを、同じデータで両立させる口。** ONTAPそのものがマネージドで動くため、SnapMirrorによる既存NetAppからの移行、重複排除・圧縮などの機能もそのまま使える。決め手は「マルチプロトコル」「既存NetApp資産の移行」。単一プロトコルで足りるならEFSかFSx for Windowsが先に立つ。

### fsx_openzfs(FSx for OpenZFS)

**スナップショット+書き込み可能クローンの流儀を、そのまま持ち込む。** 検証環境を一瞬で量産して捨てる東雲の運用を、変えずに移行できた。提供はNFS。「ZFSからの移行」「書き込み可能クローン」が要件語で、同じNFS系のEFSや多機能のONTAPと混同させるのが定番のひっかけ。

## 確認クイズ

1. 数百GBと小容量のEFSなのに、月次バッチで一時的に高帯域が必要。Burstingで詰まった。どう直す?
   → スループットモードをElastic(またはProvisioned)に変更する。Burstingは容量に比例して帯域が決まるため、小容量だと帯域が構造的に足りない。スループットモードは作成後も変更可能(パフォーマンスモードは変更不可)。

2. SMB+Active Directory+NTFS ACLでの部署別アクセス制御が必須の共有。EFSを選べない理由と正しい選択は?
   → EFSはLinux/NFS専用でSMBを話せないため棄却。FSx for Windows File Serverを選ぶ。ADに参加しNTFS ACLをそのまま使える。Multi-AZ構成は作成時に決める。

3. 同じデータセットをNFSとSMBの両方から読み、かつ既存NetAppのSnapMirrorで移行したい。どのFSxか?
   → FSx for NetApp ONTAP。マルチプロトコル(NFS/SMB)対応で、SnapMirrorにより既存NetApp資産をそのまま移行でき、重複排除も効く。
