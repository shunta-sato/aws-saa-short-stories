# 短編3: 引っ越しと四つのFSx — ファイルストレージ編

*SAA-C03 短編小説集 / storage_architecture (3/5)*

---

フォトリム社が映像アーカイブ会社「東雲アーカイブズ社」を買収した、という発表があったのは四月のことだった。堂島美咲がそのニュースを社内ポータルで読んだ三日後、彼女は移行プロジェクトのインフラ担当にアサインされていた。

「先方のシステムを、半年でAWSへ引っ越す。よろしくな」と瀬名は他人事のように言った。「ファイルサーバーが、まあ、それなりに歴史がある」

歴史がある、という言い回しの不穏さを、美咲は東雲アーカイブズ社のサーバールームで理解した。大阪にあるそのデータセンターへ、美咲は神戸から電車で通った。エレベーターを地下二階で降りると、空気が変わる。冷気と、かすかな機械油の匂い。年代物のラックの列の奥から、ファンの低い唸りが絶え間なく聞こえていた。

案内に立ったのは、五十八歳の矢吹智弘。元データセンター運用責任者だった。

「クラウドの人か」矢吹は美咲を上から下まで一瞥し、その値踏みを隠さなかった。腕を組む。「言うとくけどな、うちのファイルサーバーは複雑やぞ。NFSもSMBもある。ADで部署ごとにアクセス制御かけてる。レンダリングファームは普通のストレージやと速度が出ん。全部S3に放り込んだら終わり、て思てるんやったら帰ってんか」

「思ってません」美咲は言ったが、内心では「全部EFSに載せればだいたい片付くのでは」と思っていた。その甘さは、翌週の棚卸しで木っ端微塵になる。

---

棚卸しの結果、移行対象は大きく五つに分かれた。

ひとつ目は、社内ツール群が共有で使っている**Linux系のNFS共有**。スクリプト置き場やログ集約に使われている、ごく汎用的なファイル置き場だ。

ふたつ目は、**Windowsファイルサーバー**。これがやっかいで、プロトコルはSMB、認証はActive Directory、フォルダごとにNTFSのACLで部署別アクセス制御が効いている。「経理フォルダは経理部しか開けん。当たり前やろ」と矢吹。

三つ目が、矢吹が誇る**映像レンダリングファーム**。数十台のノードが一本の映像を分割して並列でレンダリングする。全ノードが同じ素材ストレージに猛烈な並列I/Oを叩き込むため、普通のファイルサーバーでは帯域が頭打ちになる。

四つ目は、**NetApp製のストレージ装置**。SnapMirrorという仕組みで東京と大阪の拠点間を同期しており、しかも同じデータセットをNFSでもSMBでも読む部門があった。「Linuxの解析班とWindowsの編集班が、同じ素材を別プロトコルで触ってるんや」

五つ目は、検証チームが使う**オンプレのZFSサーバー**。ZFSのスナップショットと、そこから書き込み可能なクローンを切る運用で、検証環境を量産していた。「本番のコピーを一瞬で十個作って、壊して、捨てる。これがないと検証が回らんのや」

美咲は会議室のホワイトボードに五つを書き出し、しばらく眺めてから、白状した。「これ……全部EFSでいいんじゃ、ダメですか」

「②で詰む」瀬名が静かに言った。「EFSはLinuxとNFSの世界の住人だ。SMBは話せない。Windowsファイルサーバーは載らない」マーカーを取り、五つの行の横に細い縦線を引く。「ただ、見立ては悪くない。ファイルストレージの選定は、実は属人的な勘じゃない。プロトコルと運用要件を聞けば、置き場所はほぼ決まる。FSxという家族が目的別に四人いる。①から順番に当てはめていこう」

---

「①のLinux NFS汎用共有。これはEFSでいい」瀬名は最初の一つを丸で囲んだ。「複数AZからNFSでマウントできて、容量無制限、使った分だけ課金。クラスは**EFS Standard**——リージョナル構成で複数AZにデータを複製する、いちばん壊れにくい置き方だ」

「過去ログはどうします? ほとんど読まれないんですが」

「最終アクセスからしばらく経ったファイルは、ライフサイクル管理で低頻度アクセス用の**IAクラス**(Infrequent Access)へ自動で落とせる。保存単価が下がる。逆に——」瀬名は別の枝を引いた。「再生成できる中間データ、ビルド成果物のキャッシュみたいなものなら**EFS One Zone**という手がある。単一AZに置く代わりに約47%安い。AZが飛んだら戻らないが、作り直せるデータなら惜しくない」

「ユーザーの原本みたいに、作り直せないデータは置かない。サムネイルと原本をクラスで分けた、あの請求書騒ぎと同じ理屈ですね」

「同じ理屈だ。安さには必ず、引き換えに差し出しているものがある」

ここで矢吹が口を挟んだ。「社内ツールの共有な。容量はせいぜい数百GBと小さいけど、月次バッチのときだけ一気に読み書きするんや。瞬間的に高い帯域が要る。EFSでそんな芸当できるんか」

「できます」と美咲は答えた。マネージドなのだから、負荷が来れば伸びるだろう——その程度の理解で、彼女はEFS Standardを既定値のまま作り、月次バッチの初回を迎えた。

そして転んだ。バッチが普段の三倍の時間で詰まったのだ。

「スループットが頭打ちです……」深夜、ログを見つめて美咲は青ざめた。矢吹に「できます」と言い切った手前、顔から火が出る思いだった。

翌朝、瀬名と二人でメトリクスを開いた。「EFSの性能には軸が二つある」と瀬名は画面を指した。「ひとつは**パフォーマンスモード**。汎用モードは低レイテンシ、Max I/Oは数千クライアント級の超並列向けだが一操作ごとのレイテンシは上がる。これは作成時にしか選べない。今回は汎用で正しい。問題はもうひとつの軸——**スループットモード**、帯域の決まり方だ」

「帯域の、決まり方」

「既定の**Bursting**は、帯域が保存容量に比例する。データが少なければ帯域も細く、バーストクレジットを使い切れば地を這う。このファイルシステムは数百GBしかないのに、バッチが一瞬だけ太い帯域を要求した。容量と帯域が鎖で繋がっている限り、構造的に足りない」

容量と帯域の鎖。美咲は、gp2の容量とIOPSの鎖を断ち切った日のことを思い出した。同じ形の罠に、二度はまったのだ。

「**Elastic**に切り替えます」彼女は言った。「負荷に応じて帯域が自動で増減する。使った分だけ払う。固定で確保したいワークロードなら**Provisioned**で容量と無関係に帯域を張る——でも月次バッチみたいなスパイクには、Elasticの方が合ってます」

「幸い、スループットモードは後から変えられる」瀬名は頷いた。「パフォーマンスモードと違ってな」

次の月次バッチは、普段通りの時間で終わった。美咲は矢吹に結果とともに原因と対策を報告した。言い切って転んだ分まで含めて、全部だ。矢吹は報告書を最後まで読み、「転び方の説明ができるんやったら、上等や」とだけ言った。

---

②のWindowsファイルサーバーに進んだとき、答えは美咲の中でもう固まっていた。

「ここは**FSx for Windows File Server**しかありません。SMB、AD統合、NTFSのACL——要件の三つともWindowsの言葉です。EFSはNFS専用だから土俵にすら上がれない。FSx for WindowsはネイティブにSMBを話して、ADドメインに参加して、NTFS ACLをそのまま使えます」

「つまり」と矢吹。「経理フォルダの権限設計、やり直さんで済むんか」

「既存のADドメインに参加させれば、そっくり引き継げます」

「それは……正直、助かるな」矢吹の声から、針が一本抜けた。

「ひとつだけ最初に決めることがある」瀬名が付け加えた。「可用性だ。Multi-AZ構成は作成時にしか選べない。単一AZで作って、後からマルチAZには変えられない。経理が止まると会社が止まるなら、最初からMulti-AZだ」

---

③のレンダリングファームは、地下フロアの主役だった。矢吹はラックの列を撫でるように歩きながら言った。「ここだけは譲れんで。レンダリング中、数十台が一斉に同じ素材を読みに来るんや。生半可な共有ストレージやと、帯域が先に死ぬ」

「EFSのMax I/Oでは——」美咲が言いかけると、瀬名は首を振った。

「桁が足りん。ここは**FSx for Lustre**の領分だ。Lustreはスーパーコンピュータの世界で使われてきた並列分散ファイルシステムで、数十数百ノードからの同時I/Oに、数百GB/s級の帯域で応える。それにもうひとつ、この案件向きの特技がある。S3とリンクできる」

「S3と?」

「素材は普段S3に置いておく。レンダリングのときだけLustreへロードして高速処理し、結果をS3へ書き戻す。高価な高速ストレージを常時抱える必要がない」瀬名はコスト形態も書き添えた。「scratchタイプは安価だが冗長性なし——壊れたらやり直す前提の一時領域。persistentタイプは永続保持で冗長性あり。レンダリングの中間ファイルはscratch、完成に近いデータはpersistentと使い分ける」

矢吹がにやりとした。「うちのファームはLustreやったら、ありものの構成に近いわ。話が早いな」

---

④のNetAppでは、美咲が先に問題の核心を口にした。

「同じデータをNFSとSMBの両方で読む部門があるんですよね。EFSはNFSだけ、FSx for WindowsはSMB。どっちかに寄せると、片方の部門が仕事を失います」

「だから四人目の家族がいる」と瀬名。「**FSx for NetApp ONTAP**。NetAppのONTAPがそのままマネージドで動く。NFSとSMBのマルチプロトコルで、同じデータを両方の顔から読める。重複排除や圧縮といったONTAPの芸も効く。そして、この案件の決め手は別にある」

「SnapMirror」矢吹が先に言った。身を乗り出している。「拠点間同期の、あれがそのまま使えるんか」

「ONTAP同士だからな。既存のオンプレNetAppからFSx for NetApp ONTAPへ、三十年使い慣れた仕組みのまま移行できる。プロトコルも、運用も、頭の中の地図も変えなくていい」

---

⑤のZFSサーバーは、もう答え合わせのようなものだった。

「スナップショットから書き込み可能なクローンを量産する運用——これ、ZFSの機能そのものですよね」と美咲。「だったら**FSx for OpenZFS**。OpenZFSベースだから、スナップショットも書き込み可能クローンも、オンプレの流儀をそのまま持ち込めます。本番のコピーを一瞬で十個作って壊して捨てる、あの検証フローが変わらない。提供はNFSです」

瀬名は何も足さなかった。足す必要がなかった。

矢吹が腕を組んだまま、ホワイトボードを見つめた。五つの行に、五つの答えが並んでいる。

「……つまり、こういうことか」彼はゆっくり言った。「プロトコルと運用を聞いたら、置き場所が決まる。汎用Linux共有ならEFS。SMBとADならFSx for Windows。HPC並列ならLustre。NetApp資産でマルチプロトコルならONTAP。ZFS運用ならOpenZFS。それだけか」

矢吹は美咲をもう一度見た。さっきの値踏みの目とは、少し違っていた。

「それだけです」と美咲は答えた。「FSxは四種類ある、と最初に聞いたときは身構えました。でも要件を聞く順番さえ間違えなければ、向こうから名乗り出てくれる感じです」

「魔法やのうて、対応表か」矢吹の頬が、わずかに緩んだ。「クラウドっちゅうのは、もっと既存をぶち壊して作り直させるもんやと思てた。プロトコル聞いて置き場所が決まるんやったら……まあ、こっちの資産を活かせるっちゅうことやな。悪ない」

クラウド懐疑派の古参が態度を軟化させた瞬間だった。だが矢吹はすぐに、ぴしゃりと付け加えた。

「ただし、や。話はここで終わらんで」彼は地下の奥を指した。「あの部屋には、まだテープライブラリがある。三十年分の映像原本や。それからな——回線では送りきれんペタバイト級の映像マスターが、別棟の倉庫にまるごと眠っとる。あれをどうやってAWSに上げる気や? 半年で? ネット越しに?」彼は少し声を落とした。「それにな。上げる話ばっかりしとるけど——そのデータは、どの単位で戻すんや。全部いっぺんにか? 一本ずつか? そこを決めんと、上げたところで意味がない」

美咲は計算しかけて、固まった。ペタバイト級を通常回線で送ったら、終わるのは半年どころではない。

「……それは」瀬名が腕を組んだ。「別の方法が要るな。物理で運ぶやつだ」

「物理で?」

「それは次の話だ」瀬名は薄く笑った。「今日はファイルサーバーを片付けた。テープと、回線で送れない山は——また来週、頭を抱えよう」

矢吹がふっと鼻で笑った。冷えた地下フロアに、初めて、共犯者めいた空気が流れた。

## この章の登場用語と決め手

| term_id | 物語での決め手 |
|---|---|
| efs_standard | Linux/NFS汎用共有の基本。リージョナル(複数AZ)で複製、最も壊れにくい |
| efs_infrequent_access | 最終アクセスから経過した過去データをIAへ自動移行し保存単価を下げる |
| efs_one_zone | 再生成可能な中間データ向け。単一AZだが約47%安い。AZ障害で消えても作り直せるものに限る |
| efs_performance_mode | 汎用=低レイテンシ/Max I/O=超並列だが高レイテンシ。作成時のみ選択可・変更不可 |
| efs_throughput_modes | Bursting=容量連動(小容量だと帯域不足)/Elastic=自動増減/Provisioned=固定確保。後から変更可 |
| amazon_fsx_for_all_types | FSx総称。プロトコル×運用要件の対応表で機械的に選ぶ |
| fsx_windows_file_server | SMB+AD参加+NTFS ACLが必要なWindows共有の一択。EFSはNFS専用で棄却。Multi-AZは作成時選択 |
| fsx_lustre | HPC級の超並列I/O。S3とリンクしロード/書き戻し。scratch=安価冗長なし/persistent=永続冗長あり |
| fsx_netapp_ontap | NFS/SMBマルチプロトコル+重複排除。SnapMirrorで既存NetAppからそのまま移行 |
| fsx_openzfs | ZFSのスナップショット+書き込み可能クローン運用をそのまま維持。NFS提供 |

## 確認クイズ

1. 数百GBと小容量のEFSなのに、月次バッチで一時的に高帯域が必要。Burstingで詰まった。どう直す?
   → スループットモードをElastic(またはProvisioned)に変更する。Burstingは容量に比例して帯域が決まるため、小容量だと帯域が構造的に足りない。スループットモードは作成後も変更可能。

2. SMB+Active Directory+NTFS ACLでの部署別アクセス制御が必須の共有。EFSを選べない理由と正しい選択は?
   → EFSはLinux/NFS専用でSMBを話せないため棄却。FSx for Windows File Serverを選ぶ。ADに参加しNTFS ACLをそのまま使える。Multi-AZ構成は作成時に決める。

3. 同じデータセットをNFSとSMBの両方から読み、かつ既存NetAppのSnapMirrorで移行したい。どのFSxか?
   → FSx for NetApp ONTAP。マルチプロトコル(NFS/SMB)対応で、SnapMirrorにより既存NetApp資産をそのまま移行でき、重複排除も効く。
