# 誰も住んでいないはずの家 — Organizations/Identity Center編

*SAA-C03 短編小説集 / S3-02 — security_identity_and_access*

---

`09-12 03:41:55 APIコール 1件 — アカウント末尾7743(用途登録なし)/ 前回の呼び出し記録は14か月前`

---

十二月に入って最初の経費精査で、城戸悠介の指が一つの行で止まった。AWSの請求。ただし、いつもの本番アカウントではない。買収時に東雲アーカイブズから引き継いだ支払い科目の隅で、月4,200円前後の請求が、名前も担当者もないまま息をしていた。

「跳ねた行は皆が見る。動かん行は誰も見ない——自分で言うた言葉に、自分が刺されました」城戸は乾いた声で言った。「この行、買収からずっとあります。私は17か月、見ていて、見ていなかった」

アカウントの素性は、矢吹智弘が知っていた。正確には、大阪からのチャットで真鍋一花が思い出した。

> ありました、検証用アカウント。レンダリングのテストで使ってたやつです。矢吹さんが「クラウドはまず借家で試せ」言うてはったの、覚えてます。

「……DCは畳んだが、家はもう一軒あったんか」矢吹は画面の前で腕を組んだ。畳んだはずの古巣に、畳み忘れた部屋があった。その顔から、いつもの重みのある軽口が消えていた。

「そこに、顧客のデータはあるんですか」狩野沙耶の問いは短かった。真鍋の返事は「検証用のダミーのはずです」。矢吹が首を振った。「『はず』はあかん。中を見るまで、あるかもしれん、で動くんや」

だが、中を見るには入らなければならない。誰も、この家の鍵を持っていなかった。ルートユーザーのメールアドレスは、東雲アーカイブズの旧ドメイン宛て——会社ごと消えた住所だった。一瞬、部屋が静かになった。もしあのドメインが失効して、誰か外の人間の手に渡っていたら。建物の権利書の送り先が、他人の郵便受けになっていたら。

「ドメインなら、生きてます」守屋仁が手元の台帳をめくって言った。「解約の稟議、二度出ましたけど、二度とも止めました。どこにメールが着くか確かめる前に住所を捨てたらあかん、と思ったので。……更新料は年1,400円です」

年1,400円の地味が、権利書を守っていた。旧ドメインのメールでルートのパスワードを再設定し、その場でMFAを掛け、風間祐里が東京から緊急で入って、中を検めた。見知らぬ名前のロールが二つ。作られてから2年放置されたアクセスキーが1本。そして、操作の履歴に——3か月前の日付で、API呼び出しが1件。それより古い記録は、一行もない。誰も住んでいないはずの家の廊下に、新しい足跡が一つだけ落ちていた。

「誰です、これ」

「分かりません」風間は履歴の画面を保存しながら言った。「もう一つ、悪い知らせがあります。この標準の履歴は直近90日しか遡れません。この1件は、あと数日で消えるところでした。——3か月より前にこの家で何があったかは、もう誰にも言えないんです」

---

翌朝、狩野を交えた対策会議で、風間は問題を二つに割った。

「一つ目。知らないアカウントが存在できてしまう構造を潰す。二つ目。増えるアカウントを、名札の台帳が追える形にする。——順にやります」

一つ目の答えがAWS Organizationsだった。会社のアカウントを一つの組織に束ね、支払いも作成も組織の管理下に置く。アカウントはOU——組織単位という階層に整理する。本番のOU、検証のOU、実験用のサンドボックスのOU。

「OUは家の並びです。町内会の班分けみたいなもので、班ごとに規則を継承させられる。その規則がSCP——サービスコントロールポリシーです」

「IAMポリシーと何が違うんですか」青柳凛が訊いた。「また鍵束ですか」

「いいえ。ここを混ぜると全部濁ります」風間はホワイトボードに線を引いた。「IAMポリシーは鍵束——何をしてよいかを与えるもの。SCPは塀——その班で越えられない外周を決めるものです。SCPは権限を一つも与えません。塀の内側で、それぞれの家が鍵束を配る。そして塀は、家の主人——アカウントの管理者権限を持つ人にも越えられません」

サンドボックスのOUには「使えるリージョンは東京と大阪だけ、契約系の操作は全部不可」という塀を張った。張った日の午後、青柳が試しに、サンドボックスの管理者権限で海外リージョンにインスタンスを立てようとして、弾かれた。自分の鍵束を隅々まで読んでも、拒否の行はどこにもない。

「先月の評価の順番に、出てこない拒否です」

「塀は鍵束の評価より外側にあるので」と風間。「SCPが許していない操作は、家の中でどんな鍵束を持っていても通りません。逆も言えます——塀が許していても、鍵束がなければやはり通らない。両方が許して、初めて通る」

そして旧東雲アカウントは、組織に招待したうえで隔離専用のOUへ収容した。塀はほぼ全面通行止め。調査のための読み取りだけを許す。家ごと、証拠品として封をした形だ。

「消さないんですか」と青柳。

「消すのは、何があったか分かってからです。今消せば、分からないまま終わることだけが確定します」

再設定した旧アカウントのルートの認証情報は、封筒に入って守屋の金庫へ収まった。先月からそこにある本番の封筒の、隣の段だった。金庫の中の封筒が2通になった日、と堂島美咲は台帳の更新履歴に書いた。

---

二つ目の問題は、数の問題だった。組織を整えると、アカウントは本番、検証、サンドボックス、管理、隔離の5つになる。名札の台帳をやっと1冊にしたのに、家が5軒に増えれば台帳も5冊——先月の棚卸しが、そのまま5倍になる未来が見えた。

「なりません」風間が言った。「名札は1枚のまま、家を増やします。AWS IAM Identity Center——一つのサインインで、権限のある複数のアカウントへ入る仕組みです。昔はAWS SSOと呼ばれていました」

各アカウントにIAMユーザーを複製するのではない。人はIdentity Centerに一度だけサインインし、入り口のポータルに自分の入れる家の一覧が並ぶ。試しに繋いだ美咲の画面には、家が4軒並んだ。隔離の家だけは、一覧のどこにもない。入れる人を数えられる家しか、そこには映らなかった。それぞれの家で何ができるかは、許可セットという鍵束の型で決める。「閲覧のみ」「開発者」「請求閲覧」——型を作って人とアカウントに割り当てると、対応するロールが各アカウントへ自動で配られる。

「鍵束を家ごとに手作りせずに、型で押す。増えた家にも同じ型」美咲は手帳に書いた。先月の言葉の続きが、そのまま使えた。名札を貸す設計は、家が増えても同じ文法だった。

「それで、その名札の大元の名簿はどこに置くんですか」と守屋が静かに手を挙げた。「入社と退職の台帳なら、うちの社内のActive Directoryがずっとやってます。二重に持つと、また合わんようになりますよ」

「二重には持ちません。そのためのAWS Directory Serviceです」風間が頷いた。「AWS側にMicrosoft AD互換のディレクトリを立てるか、コネクタでオンプレのADへ問い合わせを中継するか。守屋さんの台帳を正として、Identity Centerはそれを参照する。——退職の手続きをすれば、AWSの名札も同じ日に消えます」

先月、退職者の鍵を3本見つけた記憶がまだ新しい。あれを二度と手作業で探さない仕組みが、名簿の接続だった。なお、写真を見に来る一般の利用者の認証は別の話だ。あちらは顧客の話で、こちらは従業員の話——ここを混ぜないことも、板書の隅に残った。

---

年の瀬が近づくころ、検証アカウントの引っ越しで「貸し方」の設計が要った。検証環境から、本番アカウントの匿名化済みデータを読みたい。アカウントを跨いで、どう貸すか。美咲が設計レビューの主導を任された。

「道は二つあります」美咲はホワイトボードに書いた。「一つ、ロールを貸す。本番側にロールを置いて、信頼ポリシーに検証アカウントを書く。検証側はAssumeRoleで名札を借りる——先月の文法の、アカウント跨ぎ版です。二つ、リソース側に書く。バケットポリシーみたいに、リソースに直接『誰に許すか』を名指しで書く。リソースベースポリシーです。この場合、借り手は名札を替えなくていい」

「どっちにするんや」と矢吹。

「基本はロール貸しに寄せます。貸した名札は履歴に残るし、返させられるので。リソース側に書くのは、バケット単位で相手が固定の窓口だけ。——それから、ポリシーでは書けない貸し物が一つあります。検証アカウントにVPCをもう一式建てるのは無駄なので、本番側のサブネットを共有します。それはAWS RAM——Resource Access Managerの仕事です。サブネットやTransit Gatewayみたいな『場所』は、RAMで組織内に貸し出せます」

権限の委譲には、風間から二つの安全装置が付いた。検証アカウントの管理は青柳に任せる——ただし、青柳が作るロールにはアクセス許可境界を付ける。作れる鍵束の上限枠で、枠の外の権限は、本人が何をどう書いても発効しない。

「SCPと同じ塀では」と青柳。

「似ていて、階が違います。SCPはアカウントという家の塀。許可境界は、あなたが人に渡す鍵束の上限枠。家の中の委譲を縛るのがこちらです」

もう一つがセッションポリシー。監査法人が年明けに帳票を検めに来る。貸すロールの鍵束はそのままに、引き受けの瞬間に「今回はこのバケットの読み取りだけ」と絞り込みを渡す。絞ることしかできず、足すことはできない——一回きりの作業に、一回きりの小さな鍵束を切り出す仕組みだ。

最後に美咲は、増え続けるプロジェクトの問題に手を打った。学校、式場、自治体——案件が増えるたびに鍵束のポリシーが1枚ずつ増えていく。そこで、資源にも人にもプロジェクトのタグを付け、「自分のタグと同じタグの資源だけ触れる」という条件を1枚書いた。タグベースの制御——ABACと呼ぶ。案件が10増えても、ポリシーは1枚のままだった。

「鍵束を増やさずに、名札の属性で開ける扉を決める。……年内に間に合いましたね、台帳5冊の未来、回避です」

---

仕事納めの日、隔離した家の調査報告が出た。A4で一枚。分かったこと——2年放置のキーとロールの来歴は東雲時代の検証作業と矛盾しない。3か月前の呼び出し1件は、どの社員の作業とも突合できなかった。分からないこと——それが誰か。何を見たか。持ち出しがあったか。

「『持ち出された形跡はない』とは書けません」風間は狩野に言った。「書けるのは『あったともなかったとも、記録からは言えない』まで。——『無い』の証明は、記録が無ければできないんです。だから記録の話を、この季節の最後にやります」

狩野は頷いて、自分の手帳に一行書いた。漏えいが事実だった場合に、どの顧客へ、何日以内に、誰の名前で説明するか——法務側の初動手順。技術の外に、もう一枚の備えが要ることを、この一枚の報告書が教えていた。

帰り際、矢吹が隔離OUの画面をもう一度だけ開いた。塀に囲われた、誰も住んでいないはずの家。足跡は一つ。日付は9月。

「わしらが門を数えはじめる前から」矢吹は低く言った。「向こうは、家を数えとったんかもしれんな」

誰も答えなかった。港の方で、年末の汽笛が長く鳴った。

帰り道、美咲はいつもの癖で数えた。束ねた家が5軒。名札は1枚のまま。塀が3枚、上限枠が1つ、名簿の接続が1本。数えられるものは、みんな増えた。数えられないものが、一つだけ残った——9月の足跡の、主の名前。手帳の新しいページに、美咲は「記録」とだけ書いて、鞄を閉じた。

## 用語コラム — この章の登場用語と決め手

### organizations_organizational_unit(AWS Organizations OU)

**Organizations内でアカウントを階層的に束ねるコンテナ。SCP等のポリシーをOU単位で継承適用できる。** 本番・検証・サンドボックス・隔離と「家の並び=班」を分けた場面。「アカウントをグループ化して一括統制」が要件語。アカウント個別にポリシーを貼る選択肢は、数が増えた瞬間に破綻する側として出る。

### service_control_policy(サービスコントロールポリシー / SCP)

**OUやアカウントに適用する「利用可能な最大権限」の塀。権限を一つも与えない。** サンドボックスのリージョン制限や隔離OUの封鎖に使った場面。アカウントのroot・管理者にも効くのが決め手。「SCPで許可を付与する」という選択肢は常に誤り——許可はあくまでIAMポリシー側で、SCPは上限のみ。

### aws_iam_identity_center(AWS IAM Identity Center)

**従業員に複数AWSアカウント/アプリへのSSOを提供する仕組み(旧AWS SSO)。** 「名札1枚のまま家を増やす」の実体。「複数アカウントへの一元的なサインイン」「既存IdP/ADとの連携」が要件語。一般消費者向けアプリの利用者認証はCognitoの領分——従業員か顧客かで真っ先に分岐する。

### iam_identity_center_permission_set(IAM Identity Center許可セット)

**アカウント横断で使い回す鍵束の型。割り当てると対応ロールが各アカウントへ自動プロビジョニングされる。** 「閲覧のみ」「開発者」を型で押した場面。家(アカウント)ごとに手作りしない、が決め手。実体は各アカウントに作られるロールなので、評価の文法は先月のIAMと同じ。

### iam_cross_account_access(IAMクロスアカウントアクセス)

**別アカウントのロールを信頼ポリシーで引き受け可能にし、STS AssumeRoleで一時認証情報を得る標準形。** 検証→本番の「ロール貸し」の場面。「アカウント間でアクセスキーを共有する」選択肢は常に棄却——貸すのは長期の鍵ではなくロール。信頼ポリシー(誰が)+権限ポリシー(何を)の二枚一組も再確認。

### iam_permissions_boundary(IAMアクセス許可境界)

**そのユーザー/ロールが持ち得る最大権限を定める上限枠。枠外はどうポリシーを書いても発効しない。** 検証アカウントの管理を青柳へ委譲するときの安全装置。「管理者権限の一部を委譲しつつ、作成される権限の上限を保証したい」が要件語。SCP(アカウントの塀)との階の違いが定番のひっかけ。

### iam_session_policy(IAMセッションポリシー)

**AssumeRole時にセッション単位で渡す、絞り込み専用のポリシー。権限の追加はできない。** 監査法人の来訪に「今回はこのバケットの読み取りだけ」を切り出した場面。「一時的に、ロール本来より狭い権限で作業させたい」が要件語。ロール定義を書き換えずに絞れるのが決め手。

### iam_abac(ABAC / 属性ベースアクセス制御)

**プリンシパルとリソースのタグを条件キー(aws:PrincipalTag、aws:ResourceTag等)で照合し、一致で許可する方式。** 案件が10増えてもポリシー1枚のままだった場面。「プロジェクト/チームの増減にポリシー修正なしで追従」が要件語。ロールやポリシーを案件ごとに量産するRBAC側の選択肢と対で出る。

### resource_based_policy(リソースベースポリシー)

**S3バケットやKMSキーなどリソースの側に、Principal付きで書くポリシー。** 「ロールを貸すか、リソース側に名指しで書くか」の後者。借り手が自分の名札のままアクセスできるのが特徴で、相手固定の窓口に向く。主体側に付けるアイデンティティベースポリシーとの対比、ロールの信頼ポリシーもこの仲間である点が問われどころ。

### aws_resource_access_manager_aws_ram(AWS RAM)

**サブネット、Transit Gateway、Route 53 Resolverルールなど「場所」型のリソースをアカウント間・組織内で共有するサービス。** 検証アカウントにVPCを二重に建てず、本番側サブネットを貸した場面。「ポリシーでは書けない共有」が目印で、「複数アカウントでVPC/サブネットを共有」が要件語ならRAM。

### aws_directory_service(AWS Directory Service)

**Microsoft AD互換のマネージドディレクトリや、オンプレADへのAD Connectorを提供。** 守屋の社内ADを名簿の正としてIdentity Centerに繋いだ場面。「既存のActive Directoryと連携」「Windows認証」が要件語。退職処理と名札の失効が同じ日に揃うのが運用上の決め手。一般利用者の認証はCognito側。

## 確認クイズ

1. 組織内の実験用アカウント群に対し、「特定リージョン以外の利用と契約変更系の操作を、アカウント管理者を含む全員に禁止したい」。何を使うか? IAMポリシーではいけない理由は?
   → OUにまとめてSCPを適用する。SCPは利用可能な最大権限を定める塀であり、アカウント内の管理者にも効く。IAMポリシーはアカウント内の主体にしか付けられず、管理者は自分で書き換えられるため上限保証にならない。

2. 従業員300人に、10個のAWSアカウントへ職務に応じた権限でサインインさせたい。社内には既存のActive Directoryがある。最も運用負荷が低い構成は?
   → AWS IAM Identity Center(旧AWS SSO)をDirectory Service経由で既存ADと連携し、許可セットを人×アカウントに割り当てる。各アカウントへIAMユーザーを個別作成する案は、名札の複製と退職時の消し忘れを量産するため棄却。

3. 部門管理者にIAMロールの作成権限を委譲したいが、作成されるロールが管理者相当の権限を持つことは防ぎたい。何を使うか? SCPとの違いは?
   → アクセス許可境界(permissions boundary)を委譲先とその作成物に強制する。境界は個々のユーザー/ロールの最大権限の枠。SCPはアカウント/OU全体の塀であり、特定の委譲だけを細かく縛る用途には境界を使う。
