# 短編1: 請求書は嘘をつかない — ストレージ編

*SAA-C03 短編小説集 / storage_architecture*

---

月曜の朝、瀬名美咲のSlackに経理部からのメンションが刺さっていた。

「先月のAWS費用、前月比180%です。説明をお願いします」

美咲は写真共有サービス「フォトリム」のインフラを一人で見ている。ユーザーが上げる写真は月に2TBずつ増え続け、保存先はすべてS3だ。S3は壊れない、容量も無限、そう思って深く考えずに使ってきた。請求書のダッシュボードを開くと、原因はすぐに分かった。ストレージ費用。全データが**S3 Standard**に積み上がったままだった。

「アクセスログを見ましょう」と、隣の席の先輩・堂島が画面を覗き込んだ。「写真って、アップロード直後は見られるけど、その後は?」

S3のストレージクラス分析を1か月仕込んで眺めると、傾向は綺麗に出た。アップロードから30日間はよく閲覧される。その後はほとんど読まれない。ただしユーザーが過去のアルバムを開くことはあり、そのときは待たせられない。

「低頻度アクセス、でも取得は即時。教科書通りの**S3 Standard-IA**ですね」

「単一AZでよければ**One Zone-IA**がさらに2割安いが——」堂島は首を振った。「ユーザーの思い出の原本だ。再作成できないデータを単一AZに置くのはなしだ。One Zone-IAはサムネイルみたいな、消えても再生成できるデータ用にしよう」

美咲は**S3ライフサイクルポリシー**を書いた。アップロードから30日でStandard-IAへ移行、サムネイルバケットは30日でOne Zone-IAへ。書きながら、ドキュメントの注意書きに引っかかった。Standard-IAには**最小ストレージ期間**が30日ある。30日未満で消すと、残り日数分が課金される。フォトリムには「投稿から7日で自動削除されるストーリー機能」があった。これをIAに移したら、削除しても30日分払うことになる。ストーリー用プレフィックスはライフサイクルの対象から外し、Standardのまま7日で削除だけ設定した。

「それと、**取り出し料金**を忘れるな」と堂島。「IAは保存が安い代わりに、読むたびにGBあたりで課金される。頻繁に読まれるデータを移すと逆に高くつく。今回は実測で30日後のアクセスが激減してるから成立するんだ。数字を見ずにクラスを変えるのは、目隠しで引っ越しするのと同じだぞ」

ひとつ問題が残った。法人向けプランの写真は契約上の閲覧パターンが読めない。頻繁に見るテナントもあれば、年に一度のテナントもある。美咲は**S3 Intelligent-Tiering**を選んだ。アクセスを監視して自動で階層を移してくれるし、IAと違って取り出し料金がない。ただしオブジェクトごとに監視料金がかかり、128KB未満は監視対象外。法人写真は1枚平均4MBなので、監視料より階層化の削減が勝つ計算だった。

---

翌月、コストは下がり始めたが、次の課題が来た。利用規約の改定で「退会ユーザーのデータは7年保管」が決まったのだ。7年間、誰も読まないデータ。

「**Glacier**系の出番ですね。Deep Archiveなら最安です」

「取り出し要件は?」

「警察からの照会対応で、48時間以内に提出できればいいそうです」

**S3 Glacier Deep Archive**は標準取り出しで12時間、バルクなら48時間。要件に収まる。最小ストレージ期間は180日だが、7年保管なら問題にならない。美咲はライフサイクルに「退会から180日後にDeep Archiveへ」を追加し——堂島に止められた。

「移行の単価×オブジェクト数を計算したか? 写真は数億オブジェクトある。**ライフサイクル移行リクエスト**は1件ごとに課金されるし、Glacier系は1オブジェクトに40KBほどメタデータが付く。小さいファイルを大量に流し込むと、保存費の節約を移行費が食い潰す」

計算し直すと、サムネイル(平均50KB)を含めるとほぼ利益が消えた。退会データはまずバッチでtar固めにして、大きな塊だけをDeep Archiveへ送ることにした。S3のライフサイクルにはオブジェクトサイズフィルタもあるので、128KB未満は移行対象外という保険も入れた。

その設定が実って半年後、本当に照会が来た。美咲は落ち着いて復元ジョブを発行し——画面の前で青ざめた。間違えて本番のアルバム1件もDeep Archiveに落としていたことが、ユーザーからの「写真が開けない」という問い合わせで発覚したのだ。Deep Archiveに**迅速取り出し(Expedited)は存在しない**。最短でも標準の12時間。もしこれがGlacier Flexible Retrievalだったら1〜5分の迅速取り出しが選べたのに。「即時アクセスが要るかもしれないデータをDeep Archiveに置くな」を、美咲は身体で覚えた。

---

物語はもう一幕ある。フォトリムは動画機能を始め、編集チームから「アップロードが遅い、たまに失敗して最初からやり直しになる」と苦情が来た。動画は1本3〜8GB。そもそもS3のPutObjectは5GBまでで、それ以上は**マルチパートアップロード**が必須だ。パート分割して並列で上げれば速くなり、失敗してもそのパートだけ再送すればいい。海外スタジオからの転送が遅い件は、エッジ経由でアップロードを高速化する**Transfer Acceleration**を併用した。堂島はもう一つ釘を刺した。「中断したまま放置されたマルチパートは、見えないのに課金され続ける。未完了アップロードを7日で自動破棄するライフサイクルルールを必ず入れろ」

最後に、編集チームの作業場の話。動画編集サーバーはEC2で、複数台から同じ素材を共有したいという。美咲は一瞬**EBSのMulti-Attach**を考えたが、あれはio1/io2限定・同一AZ限定で、クラスタ対応ファイルシステムが前提の特殊解だ。普通のLinux共有なら**EFS**——複数AZからNFSでマウントでき、使った分だけ課金される。編集が終わった素材はEFSのライフサイクル管理でIAストレージクラスへ自動移行。一方、各編集サーバーのスクラッチ領域は共有不要なので、gp2より2割安くIOPSを独立設定できる**EBS gp3**に統一した。

経理部への翌月の報告で、美咲はこう書いた。

「ストレージのコストは、容量ではなく『データの読まれ方』で決まります。アクセス頻度、取得までの待てる時間、再作成できるか、いつ消すか。この4つの質問に答えれば、置き場所はほぼ自動的に決まります」

請求書は嘘をつかない。だが、正しく設計すれば、ちゃんと味方になる。

## この章の登場用語と決め手

| term_id | 物語での決め手 |
|---|---|
| s3_standard | アップロード直後30日の高頻度アクセス期。取り出し料金なし |
| s3_standard_ia | 低頻度だが即時取得・複数AZ耐久性が必要な写真原本 |
| s3_one_zone_ia | 再生成可能なサムネイル。単一AZで約2割安 |
| s3_lifecycle_policy | 30日でIAへ移行、7日で削除など日数ベースの自動化 |
| s3_minimum_storage_duration | IA=30日。7日削除のストーリー機能をIAに移すと損 |
| s3_retrieval_fee | IA系はGB取り出し課金。頻繁に読むデータは移すと逆転 |
| s3_intelligent_tiering | アクセスパターン不明な法人データ。監視料あり・128KB未満は対象外・取り出し料金なし |
| s3_glacier_deep_archive | 7年保管・48時間以内取り出しの退会データ。最小180日 |
| s3_glacier_retrieval_options | Deep ArchiveにExpeditedなし(標準12h/バルク48h)。Flexibleなら迅速1〜5分 |
| s3_lifecycle_transition_cost | 移行リクエスト課金+Glacier系のメタデータ約40KB。小オブジェクトはtar固め |
| s3_multipart_upload | 5GB超は必須。並列・部分再送。未完了パートの自動破棄ルール |
| transfer_acceleration | 海外からのアップロードをエッジ経由で高速化 |
| ebs_gp3 | スクラッチ領域。gp2より安くIOPS独立設定 |
| ebs_multi_attach | io1/io2限定・同一AZ・クラスタFS前提の特殊解。汎用共有には選ばない |
| amazon_efs | 複数AZ・複数インスタンスからのNFS共有の標準解 |
| efs_lifecycle_management | 最終アクセス基準でIAへ自動移行(削除はしない) |

## 確認クイズ

1. 投稿から7日で自動削除されるデータをStandard-IAに置いてはいけない理由は?
   → 最小ストレージ期間30日が適用され、削除後も残り日数分が課金されるから。
2. Intelligent-TieringがStandard-IAより有利になる条件を2つ。
   → アクセスパターンが不明/変動する。取り出し料金を払いたくない(ただし監視料と128KB制限に注意)。
3. 「12時間以内に取り出せること」が要件のアーカイブにDeep Archiveは使えるか?
   → 標準取り出しが12時間なのでぎりぎり可だが余裕がない。確実性が要るならGlacier Flexible Retrieval(迅速1〜5分/標準3〜5時間)を検討する。
