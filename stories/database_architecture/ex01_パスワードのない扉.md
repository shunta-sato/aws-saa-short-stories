# 幕間 パスワードのない扉 — IAMデータベース認証

*SAA-C03 短編小説集 / S4幕間01 — 用語集外の頻出トピック補強(幕間)*

---

四月も半ばの火曜は、風間祐里の月次訪問の日だった。

その朝、青柳凛は例外台帳の当番だった。毎週、例外扱いの鍵の期限を数える——冬に決めて、春になっても続いている当番仕事だ。合鍵台帳のDBの頁を開くと、シークレットが11本並んでいる。8本は90日で機械が回す。3本は例外の札付き。数え終えて消し込んで、いつもならそれで終いだった。

その日に限って、青柳の手が止まった。

隣の島に、先々週から新しい席がある。真鍋一花はモニターに向かって何かを数えている最中で、青柳は誰にともなく、口の中の考えを外に出した。

「……回すのは、機械化したんですよ。90日で勝手に替わる。でも、これ、そもそも」

「そもそも?」と真鍋が顔だけ向けた。

「そもそもパスワードっていう物が要るのかな、って。名札の世界は、とっくにそうなってるんです。人間の合鍵は廃止して、役割の名札を短時間だけ借りる形にした。なのにDBの扉だけ、まだ物の鍵で開けてる」

「いい疑問です。答え、あります」

声は戸口からした。風間が、旅行鞄を席に置くより先に答えていた。

「IAMデータベース認証。RDSとAuroraの、MySQL系とPostgreSQL系で使えます。パスワードの代わりに、IAMが発行する認証トークンで扉を開ける。トークンの寿命は15分。EC2やLambdaはロールで受け取るので——」

「——DB用の長期の秘密そのものが、消える」青柳が先を言って、それから少し赤くなった。「すみません。つい」

「正解を取られるのは、いい朝です」風間は笑わずに言ったが、声は笑っていた。「補足だけ。接続は暗号化——TLSが必須です。トークンは鍵というより、名札を見せて通る通行証なので、通り道が見えていては駄目」

ホワイトボードの隅には、冬から消されずに残っている一行がある。**名札は、首から下げる。机に置かない。**風間はその下に、同じ几帳面な字で書き足した。

**扉には、合鍵より通行証。**

「ただし」と風間は続けた。「全部の扉をこれにしよう、は間違いです。接続を秒間に何本も張っては切るような使い方だと、認証の手間が積み上がる。接続が非常に多い用途には勧めない、と公式にも線が引いてあります」

「あ——」青柳は、行列の週に真鍋が描いた電話線の図を思い出した。「だから、Proxyと組むんですね。電話線は束ねて使い回して、認証は通行証で。張り替えが減れば、手間も積まれない」

「定石です。それから、合鍵台帳が空になるわけでもない。この方式が使えないエンジンもあるし、外部連携の鍵は残る。……なので、どこから始めます?」

「数えます」と青柳が言うのと、「1日何回開く扉です?」と真鍋が言うのが、ほとんど重なった。二人は一瞬、互いを見た。先を越された、という顔と、同類がいた、という顔が、両方の顔の上で同時に起きた。

数えた結果は、その日の夕方に出た。社内ツール系の扉が4つ——開くのは1日に数十回、張りっぱなしでもない。ここから通行証に替える。本番の高頻度の扉はProxyの後ろに置いたまま、次の四半期に。例外の3本のうち1本は、そもそもこの方式で不要になる。

「例外台帳が、1頁薄くなりました」

締めの報告で青柳がそう言うと、風間はノートを開いて、項目の横に正の字の最後の一画を足した。それから、消し込んだ行の頭に、小さな花丸をひとつ。

「鍵の置き場所を良うするんやのうて」矢吹智弘が唸った。「鍵屋ごと畳んだんか。おまえの当番仕事、地味な顔して、ようそんなん見つけてくるな」

「毎週数えてると、数字より先に、数えなくていい方法を考えるようになるんです」

「ええ癖や。……おい真鍋、聞いたか。こっちの倉庫番も、数えるぞ」

「聞きました」真鍋は自分のモニターから目を離さずに言った。「うちより二つ下やのに、生意気やなと思って聞いてました」

部屋が少し笑って、当番の週がまた一つ終わった。数える仕事は、数を減らすための仕事だ。台帳は1頁薄くなり、薄くなった分だけ、この部屋の夜は少しだけ静かになる。

## 補講コラム — IAMデータベース認証(IAM database authentication)

**パスワードの代わりに、IAMが発行する有効期限15分の認証トークンでRDS/Auroraに接続する仕組み。** 対応はMySQL/MariaDB/PostgreSQL系のRDSおよびAurora(Oracle/SQL Serverでは使えない)。DB側に対応する認証方式のユーザーを作り、IAMポリシーで接続権限(rds-db:connect)を許可する。EC2/Lambdaはロールでトークンを得るため、DB用の長期パスワードの保管・ローテーション運用そのものが消える。接続はTLS(SSL)必須。

試験での決め手: 「DBの認証情報を保管せずにIAMで一元管理したい」ならIAMデータベース認証。「接続確立が非常に多いアプリには非推奨」という制約があり、RDS Proxy(接続プール)との併用が定石として問われる。ひっかけは2つ——「Secrets Managerのローテーションが常に唯一の正答」ではないこと、「すべてのRDSエンジンで使える」は誤りであること。

## 確認クイズ

1. RDS for PostgreSQLへ接続するEC2上のアプリについて、(a)DBパスワードを保管せずIAMで認証を一元化したい、(b)ただしこのアプリは接続の確立が非常に多い。どう設計するか?
   → (a)IAMデータベース認証(ロールで15分有効のトークンを取得、TLS必須、rds-db:connectを許可)。(b)接続確立が多い用途には認証オーバーヘッドが積むため非推奨——RDS Proxyを挟んで接続をプールし、張り替え自体を減らした上で組み合わせる。なお、IAM認証非対応のエンジンや外部連携の資格情報にはSecrets Manager(自動ローテーション)が引き続き正答側になる。
